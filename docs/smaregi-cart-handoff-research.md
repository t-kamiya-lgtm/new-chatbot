# スマレジEC連携によるチャットシステムのPII非保持化 — 調査結果

対象リポジトリ: `t-kamiya-lgtm/pm-chat-bot`(ブランチ`claude/chatbot-payment-system-hx4hqh`)の構想検討に対する調査。
本ドキュメントは調査専用リポジトリ`t-kamiya-lgtm/new-chatbot`側に置く(pm-chat-bot側への実装変更は行っていない)。

引き継ぎ元の「次にやってほしいこと」3点について、Web公開情報(スマレジEC・リピート ヘルプセンター等の検索結果)から調査した。
**注記**: 実行環境のネットワーク制限により`ec.smaregi.jp`ドメインへの直接アクセス(WebFetch)がブロックされており、
検索エンジンのスニペット経由での情報収集に限られた。断定的な確認が必要な項目は「要問い合わせ」と明記する。

## 1. 外部からカートに商品追加/事前入力チェックアウトURL発行は可能か → **部分的にYES**

スマレジEC・リピートには **「カートインURL機能」** が存在する。

- 商品登録と同時に自動発行される、商品ページを経由せず直接カートに投入できるURL
  (`https://ドメイン名/cart/add.php?pcode=商品番号&code=商品管理番号`)
- 数量指定、スタッフID指定(`sf=`パラメータ)などのクエリパラメータ拡張が可能
- 非同期通信用スクリプトを設置すれば、クリック時にスマレジ側の買い物かご画面へ遷移させず
  自サイト上にメッセージのみ表示させることも可能(= チャットUI内に留まったまま「カートに入れました」表示ができる)

これはShopifyのカートpermalinkに近い仕組みで、**「チャットが商品提案 → カートインURLでスマレジのカートに投入 →
決済・個人情報入力はスマレジ純正チェックアウトに委ねる」という構想の中核部分は技術的に実現可能**と判断できる。

一方で、確認できなかった/懸念点:

- **顧客(会員)識別パラメータが見当たらない**。検索できた範囲のパラメータは`pcode`(商品番号)・`code`(商品管理番号)・
  `sf`(スタッフID)のみで、「このチャットユーザー=スマレジのどの会員か」をURLに乗せて自動関連付けする手段は
  確認できなかった。つまりチャット側で会員登録済みのユーザーであっても、決済時にスマレジ側へ別途ログインする
  operationが必要になる可能性がある(スマレジの通常ログインセッションは2時間、「自動ログインを有効にする」設定で
  365日間維持されるとの情報はあるため、一度ログインすればその後は维持されやすい)。
- 「事前入力済みチェックアウトURL」(住所・カード情報まで埋めた状態のURL)に相当する機能は検索範囲では
  確認できず、カートインURLは**あくまで「カートに商品を入れる」までの機能**と考えるのが安全。
  住所入力・決済自体はスマレジ側の通常チェックアウト画面(会員なら住所は再入力不要)に遷移する形になる。

**→ 要問い合わせ(スマレジ開発者サポート)**: カートインURLまたは別APIで、既存のスマレジ会員IDと紐付けた状態で
カート投入・チェックアウトへ誘導できるか(会員の再ログインを省略できるか)。

## 2. 定期購入の周期ごとの金額指定・初回特別価格・クーポン適用は表現できるか → **条件付きYES(要検証)**

以前廃止の原因になった制約(受注API `periodical_order`が初回受注データをそのまま2回目以降にコピーし、
金額を個別指定する手段がなかった)は **受注APIを使った事後連携の話**であり、
**スマレジ純正チェックアウト(お客様が直接申し込む定期購入)の価格ロジックとは別の経路**であることが分かった。

純正チェックアウト側の価格決定は以下のように動作するとみられる:

- 定期購入は「標準販売価格」をベースに、リピート割引・顧客ランク割引が都度計算される
  (=固定金額を毎回コピーするのではなく、都度標準価格から再計算する方式に見える)
- **「定期継続時のクーポン利用機能」**という機能が存在し、クーポン管理画面で「利用条件(購入フロー)」に
  「定期継続購入(お申込単位)」を選択し、「範囲指定」(例: 3~4回目のみ)または「回数指定」(例: 2回ごと)で
  クーポンを適用する周期を指定できる。これはまさに「初回特別価格は初回のみ、2回目以降は通常価格」という
  今の要件を、受注APIを介さず**スマレジ純正チェックアウト機能の範囲内**で表現できる可能性を示している。

つまり、以前ぶつかった制約は「受注APIでperiodical_orderに金額を個別指定できない」という**API連携特有の制約**であり、
「純正チェックアウトでお客様が定期購入を申し込む」という今回の別案の経路とは別問題である可能性が高い。
これが本当に成り立つなら、以前の廃止理由(a)は今回の構想には当てはまらない。

**→ 要問い合わせ/要検証**:
1. 「定期継続時のクーポン利用機能」のリリース時期(以前の廃止判断より後に追加された機能である可能性がある。
   検索範囲では正確なリリース日は確認できなかった)。
2. 今の仕様にある「よりどり(セット品)内訳の定期継続」「アドオン商品の同時定期購入」「頻度自動切替(お試し→本品)」
   といった、`subscription-renewal.ts`に実装済みの独自ロジックが、スマレジ純正の定期購入機能で同等に表現できるか
   (これらは受注API側の話ではなく、そもそも「スマレジの定期購入商品登録」機能でどこまで柔軟な設定ができるかの確認が必要)。

## 3. 決済手段の一本化(代引き・後払い)について → **部分的に有望、契約面の検討が必要**

スマレジEC・リピートの純正チェックアウトは、クレジットカード・キャリア決済(ドコモ払い/auかんたん決済/
ソフトバンクまとめて支払い)・AmazonPay・楽天ペイに加えて、**複数の後払い決済サービス**
(NP後払い、GMO後払い、ニッセン@払い、ATODENE、クロネコ代金後払い、コンビニ後払い等)との連携に対応している。

現行の代引き・後払いフローは、現行実装(`src/lib/adapters/core-system.ts`)を見ると
「与信判定・請求書発行・入金確認は自社の基幹システム側の責務」という設計になっている。
スマレジ純正チェックアウトの後払いは、いずれも**外部の後払い決済代行会社(NP後払い等)が与信・請求書発行・
入金確認を担うサービス**であるため、技術的には決済手段を一本化できる可能性が高い一方、

- 現行の基幹システムの与信判定ロジック・請求書発行フローとは別物(外部決済代行への切り替えになる)
- 各後払いサービスとの契約・手数料が別途発生する
- 「代引き(COD/配送時現金回収)」そのものへの対応は検索範囲では確証が得られなかった(後払い系サービスは
  代引きとは異なる)

という、技術選定というより**契約・業務フローレベルの意思決定**が必要になる。

**→ 要問い合わせ**: 代引き(配送時現金回収)自体への対応有無、および後払い各社の与信基準・加盟审查の要否。

## 総合評価と推奨アーキテクチャの方向性(暫定)

以前の受注API連携廃止の理由は「受注APIのperiodical_order特有の制約」であり、**「純正チェックアウトへのカートイン
方式」という今回の別案とは別の経路の話**である可能性が高いことが分かった。技術的な実現性は、
少なくとも「商品をカートインURLでスマレジ側に渡す」部分については有望と判断できる。

一方で、以下は検索情報だけでは断定できず、**スマレジ開発者サポートへの直接確認が必須**:

1. カートインURL(または別API)で既存会員IDと紐付けた状態でチェックアウトへ誘導できるか(再ログイン省略の可否)
2. 「定期継続時のクーポン利用機能」のような価格制御機能で、現行の全ロジック
   (初回特別価格、よりどり内訳の継続、アドオン同時定期、頻度自動切替)を再現できるか
3. 代引きへの対応有無、および後払い各社利用時の契約・審査条件

これらが確認できるまでは、以下を暫定の折衷アーキテクチャ案として検討を進めるのが現実的:

- **チャット側DBにはPIIの実データを持たない**方針は維持しつつ、決済手段によってハンドオフの形を分ける
  - カード決済(単発・定期): カートインURLでスマレジ純正チェックアウトへハンドオフ → PIIはスマレジ側のみに保持
  - 代引き・後払い: 上記2・3の確認結果によって、スマレジ純正の後払いサービスに統一できるか、
    現行の基幹システム連携を維持するかを判断
- チャット側DBには「スマレジ会員ID」「スマレジ受注ID」等の参照キーのみを保持し、
  `CustomerDetailView`等の管理画面で氏名・住所等の表示が必要なタイミングでスマレジAPI(受注API/会員API、
  既存の`smaregi-client.ts`のような薄いクライアントで実装可能)から都度取得する
- `subscription-analysis`等の分析ダッシュボードは、氏名・住所等の実PIIには依存していないはずなので影響は
  比較的小さいと想定されるが、要件定義時に依存関係を再確認する

## 4. 追加調査: primedirect.jp実際のAPI仕様(カートAPI/カートコンバージョンAPI/受注API/ログインAPI)確認

上記1〜3はWeb検索スニペットに基づく一般論だったが、実際のprimedirect.jp(スマレジEC上に構築)のAPI仕様書を
確認できたため、以下は一次情報に基づく確定的な知見に更新する。

### 4.1 前提の訂正: primedirect.jpとスマレジ・通販ゲートの関係

- **primedirect.jpはスマレジEC・リピート/一元管理上に構築されたECカートシステムそのもの**(引き継ぎ時点の
  想定通り)。
- **通販ゲートはスマレジとは別サービス**で、primedirect.jp(スマレジ)側の受注データをAPIで通販ゲートへ
  連携している(=現状の「一般のEC注文」はスマレジ→通販ゲートの自動API連携が既に稼働している)。
- 一方、**チャットシステムの注文は現状この経路に乗っていない**(Stripe等で決済しチャット側DBに保存 →
  スタッフがCSV書き出し→通販ゲートへ手動取込)。つまりチャットの注文だけが、primedirect.jp本体の注文
  データとして存在しない「ないショップ」に分岐している状態と考えられる。

→ **もしチャット経由の注文を今回のカートAPI経由でprimedirect.jpの正式な注文として作成できれば、
既存の「スマレジ→通販ゲートAPI自動連携」にそのまま乗ることができ、現状チャット注文だけ発生している
CSV手動取込作業自体が不要になる可能性がある。** これはPII非保持化とは別軸だが、業務効率の観点で大きい。

### 4.2 カートAPI(`cart/confirm`, `cart/checkout`)の仕様確認結果

- サーバー間APIで、住所(氏名・フリガナ・電話番号・郵便番号・住所等)を**リクエストパラメータとして毎回渡す**方式。
  Shopifyのカートpermalinkのような「顧客がスマレジ純正フォームへ直接入力する」リダイレクト型ではなく、
  **呼び出し元(チャット)が入力内容を集めてAPI経由で送信する**方式。
  → 「チャット側DBに保存しない」は実現できるが、「チャットのサーバーが個人情報に一切触れない」までは
  この方式単体では実現しない。目指すゴールが**非保存**か**非接触**かで評価が変わる点は要認識合わせ。
- カード番号を直接渡すフィールドはなし。`get_card=on`(GMOのみ有効)という、既存登録カードを参照する
  パラメータのみ存在。新規カード登録は別のトークン化フォーム(GMO等)経由と推測されるが、今回の資料には
  含まれず、別途確認が必要。
- `cart/confirm`のレスポンスに`teiki_cycle_sets`(定期サイクル)・`coupon_list`があり、
  カート内商品ごとに`teiki_cycle_set`(どのサイクルで送付するかのグループ)を持てる。定期購入商品も
  同じカートAPI経由で申込可能と考えられる。

### 4.3 ログインAPI(`cart/login`)の仕様確認結果 — アーキテクチャ上の最重要な分岐点

`email`+`password`をPOSTすると、`customer_id`・`session_name`・`session_id`(+ `redirect_url`)が返る。
この`session_name`/`session_id`が、カートAPIのサンプルコードで使われている`Cookie`ヘッダの値そのもの。

これにより「カートAPIがセッションCookie前提」という前回の疑問点は解消したが、代わりに**新たな設計判断**が
必要になった:

- **会員としてログインさせる場合**: チャット側がスマレジEC会員の**メールアドレス+パスワードを一時的に
  受け取り**、ログインAPIに渡す必要がある。パスワードは非保存でも、チャットが認証情報を一時的にでも
  扱うこと自体がセキュリティ・UX上の懸念になりうる(「チャットボットにECサイトのパスワードを入力させる」
  という体験は一般的にフィッシング耐性の観点で避けたいパターン)。
- **ゲスト(非会員)として都度チェックアウトする場合**: `customer_id=0`を指定すれば、ログイン不要で
  カートAPIを利用できる(cart/confirmの仕様に明記)。パスワードを一切扱わずに済む一方、
  リピート顧客であっても毎回住所等を入力し直す必要があり、「顧客管理画面での継続顧客把握」
  (`tenureMonths`等、既存の`customer-detail.ts`の機能)との相性が悪くなる可能性がある。
  ただし受注API側には`customer_id=-1`で「メールアドレスによる名寄せで顧客新規作成」という指定もあり、
  ゲスト注文でもメールアドレス一致で同一顧客として名寄せされる可能性はある(要確認)。

→ **これは技術調査というより、事業判断が必要な分岐点。** 「ゲストチェックオンリーで割り切る」か
「会員ログインの手段を別途検討する(例: 決済確定前の一度だけ、チャットの外の別画面でログインしてもらい
トークンだけ受け取る等)」か、方針を先に決めた方が以降の調査が効率化する。

### 4.4 サンドボックス環境: なし

テスト環境が存在しないため、動作確認は本番環境で行う必要がある。実装時は少額・自社宛のテスト注文を作成し、
即キャンセル/返金する等の安全な検証手順を別途設計する必要がある。

### 4.5 更新後の残課題リスト

1. 会員ログイン方式の方針決定(4.3、要事業判断)
2. カード新規登録のトークン化方式(GMO等の決済代行側の仕様書が必要)
3. 定期購入(`teiki_cycle_sets`)をカートAPI経由で申し込んだ場合の、2回目以降の金額決定ロジック
   (受注API仕様の`periodical_order.custom_teiki_count`等が「受注作成時の定期情報」として存在するが、
   既存の`periodical_order_id`を指定した追加受注作成が可能かは受注API仕様書だけでは断定できず)
4. 定期継続時のクーポン適用機能(前回調査時点でWeb検索のみで確認、一次情報での確認が未了)
5. 会員登録・住所取得専用API(顧客API)の仕様
6. 有効な支払方法(`payment_methods`)の実際の値一覧(代引き・後払いが現契約で有効か)
7. 本番環境での安全なテスト手順の設計(サンドボックスなしのため)
